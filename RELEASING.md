# Releasing

A release is one command on your machine, `just release`, and a GitHub workflow that runs when its tag is pushed. This guide covers both, and the commit messages that become release notes.

## Versions

The API, web UI and image share one [Semantic Versioning](https://semver.org) version. It lives in `api/pyproject.toml` (with `api/uv.lock`) and `web/package.json`; `just version` prints it and fails if the files disagree. Only `just release` changes it.

While the version is `0.x`:

| Commits since the last release | Next version |
|---|---|
| Only `fix` or `perf` | Patch (`0.1.0` → `0.1.1`) |
| Any `feat` | Minor (`0.1.0` → `0.2.0`) |
| Any breaking change | Minor (`0.1.0` → `0.2.0`) |

Pre-releases use `-alpha.N`, `-beta.N` or `-rc.N` (`0.2.0-rc.1`); other forms are refused. uv writes them in PEP 440 form in `pyproject.toml` (`0.2.0rc1`), and the API reports that form.

## Commit messages are release notes

Notes are generated by [git-cliff](https://git-cliff.org) from [Conventional Commits](https://www.conventionalcommits.org) (`cliff.toml`):

- `feat`, `fix` and `perf` commits become entries under **Features**, **Fixes** and **Performance**. Write their subjects for users: what changed for them, not how.
- A commit marked breaking (`feat!:`, `fix(api)!:`, or a `BREAKING CHANGE:` footer) is listed under **Breaking Changes**, whatever its type.
- Everything else (`docs`, `test`, `chore`, `ci`, `build`, `refactor`, `style`), merge commits and non-conventional messages are left out. Use those types for changes users would not notice, including story bookkeeping.
- Scopes are hidden, except the components `api`, `web` and `docker`, which show as **api:** and so on. Story, task and review scopes (`story-14.2/task-6`) never appear.
- The `!` goes after the scope: `feat(api)!: …`. `feat!(api): …` is not a conventional commit and is dropped.

Preview the notes for everything since the last release:

```bash
just changelog
just changelog --tag v0.2.0   # with the heading the release will have
```

## Cutting a release

From an up-to-date `main` with a clean working tree:

```bash
just release --dry-run        # show the version and notes; changes nothing
just release                  # version computed from the commits
just release minor            # or patch / major
just release 0.3.0-rc.1       # an explicit version (required for pre-releases)
```

`just release` refuses to run off `main`, with uncommitted or untracked files, when `main` differs from `origin/main`, for an existing tag, for a version not newer than the last release, and when there is nothing to release. Otherwise it:

1. Shows the version and notes.
2. Sets the version in `api/pyproject.toml`, `api/uv.lock` and `web/package.json`.
3. For a stable version, adds its section to `CHANGELOG.md` below the header. If `CHANGELOG.md` already has a section for the version (written by hand), that section is kept and used. Pre-releases leave `CHANGELOG.md` alone; it lists stable releases, and each stable release's notes cover everything since the previous stable release.
4. Commits `chore(release): vX.Y.Z` and creates the annotated tag `vX.Y.Z`.
5. Asks `Push vX.Y.Z to origin? [y/N]`, then pushes the commit and tag together.

If anything fails, or you answer no, `main` is reset to where it was and the tag is deleted. Repository git hooks do not run for the release commit, tag and push.

After Renovate updates uv, the release commit may also change the `revision` line in `api/uv.lock` (the pinned uv rewrites it). Dependency versions are not affected.

## What the workflow publishes

Pushing the tag starts [`.github/workflows/release.yml`](.github/workflows/release.yml) (watch it with `gh run watch` or on the Actions tab):

1. **Verify:** the tag must equal the repository's version and be on `main`. The notes are the version's `CHANGELOG.md` section, or generated notes for a pre-release.
2. **Image:** builds `linux/amd64` and pushes `ghcr.io/craquehouse/vintagestory-server` as `X.Y.Z`, `X.Y` and `latest` (a pre-release gets only `X.Y.Z-rc.N`). Adds signed build provenance and an SPDX SBOM attestation for the image.
3. **Release:** creates the GitHub release with the notes and `sbom.spdx.json` attached, marked as a pre-release when it is one. It runs only if the image job succeeded.

Users verify an image as described in the [README](README.md#verifying-an-image).

### First release: make the package public

The first push creates the `vintagestory-server` package as **private**, linked to this repository. Once, after the first release: open the package from the organization's **Packages** tab → **Package settings** → **Change visibility** → **Public**. This cannot be undone. Until then, pulls need a GitHub login with access to the repository.

## When something goes wrong

- **A job failed for a transient reason** (registry or network errors, a runner problem): **Re-run failed jobs** on the run. Image tags and attestations are simply pushed again. If the **release** job fails after `gh release create` already created the release (for example while uploading the SBOM), a re-run fails with "already exists": finish it by hand (`gh release upload vX.Y.Z sbom.spdx.json`, `gh release edit vX.Y.Z --notes-file notes.md`) or delete the release (`gh release delete vX.Y.Z`) and then re-run.
- **A job failed because of a bug in the workflow or the code:** a re-run uses the workflow file and code of the tagged commit, so a fix pushed to `main` does not reach it. Fix it on `main`, then cut the next version (a new patch or pre-release) instead of reusing the tag.
- **A broken release must be withdrawn:** delete the GitHub release (`gh release delete vX.Y.Z`) and, if needed, the package version on GHCR. Do not reuse the version: tags are cached by users and mirrors. Cut the next patch version with the fix.
- **The tag was pushed but `CHANGELOG.md` is wrong:** fix `CHANGELOG.md` in a normal commit; edit the GitHub release notes with `gh release edit vX.Y.Z --notes-file …`.
